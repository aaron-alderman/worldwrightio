How Worldwright works

One platform, one world, many ways to inspect it.

Worldwright combines a collaboration philosophy, an authored language stack, a replayable runtime substrate, and multiple projections for different people working on the same decision.

The philosophy

The workspace is not outside the world. It is part of the world.

In the narrative foundation for Worldwright, the system begins with a context, not with a pile of tools. Atoms exist, maps transform them, and witnesses make process holdable over time. That is why error, policy, simulation, repair, and acceptance can all live in the same inspectable place.

World first

Start from context, not from disconnected software pieces.

A world is the bounded place where evidence can exist, change, be witnessed, and be remembered.

Witness first

Process matters as much as state.

A witness is how the platform preserves what happened, under which conditions, with which inputs and outputs.

Error first-class

Failure is not side noise.

Disagreement, failed process, and unsafe promotion are part of the world model, so they can be inspected instead of hidden.

Healing without erasure

Repair should preserve the path.

The platform is designed so a world can heal, learn, and continue while keeping witness of the break.

Operational consequence

A decision is not just an answer. It is a witnessed path through evidence, disagreement, policy, repair, and acceptance.

That is why Worldwright can feel like a scientific workspace, a runtime, and a governance surface at the same time: they are all views over one evolving world.

DESIRE language

DESIRE is the authored language for declaring how the world behaves.

DESIRE is the syntax of the declarative world. It is where workflows, views, policies, adapters, and domain meaning can be written in authored form instead of being buried in hidden runtime glue. The goal is to keep more of the world's meaning visible, inspectable, and explainable.

Layer 0

Execution kernel

Small replayable substrate for bounded operations. No business or UI semantics.

Layer 1

Relational Virtual Machine core

The durable authored substrate: contexts, atoms, maps, witnesses, and machines.

Layer 2

Contracts and lowering

Where authored semantics become explicit lowering and orchestration policy.

Layer 3

Application language

The richer human-facing language for workflows, views, policies, adapters, and domains.

The important boundary is simple: if something is product meaning, workflow meaning, or world meaning, it should increasingly live in DESIRE. Host code should stay limited to transport, filesystem, project persistence, environment, and process boundaries.

Illustrative DESIRE-style workflow

module TemperatureGrowthDecision

process TemperatureReview {
  states {
    SimulationState
    MeasurementState
    DecisionState
  }
}

command RunSimulation
command IngestMeasurement

policy PromotionGate {
  requires simulation_witness
  requires observed_measurement
}

view DecisionSurface {
  show simulation_witness
  show observed_measurement
  show disagreement_record
  show decision_state
}

This is the core idea: declare the workflow, the policy gate, and the view in the language itself so the world can explain how the decision was meant to work.

RVM

RVM is the Relational Virtual Machine beneath the language.

Today’s RVM forms still matter because they provide the minimal graph model that can be parsed, validated, lowered, replayed, and inspected. This is the layer that helps keep the substrate portable and trustworthy.

Core ideas in authored form

context Lab
atom Hypothesis
map CompareSimulatedToObserved
witness DisagreementOpened
machine PromotionReview

These forms are not the whole application language. They are the stable authored substrate that richer semantics can lower into.

Why it matters

Replay and reflection depend on keeping this core small.

The Relational Virtual Machine holds the minimal authored model that lets the platform preserve accepted history, compare states, inspect witness trails, and keep one world coherent as it changes. DESIRE gives teams a richer surface; RVM keeps that surface grounded in something replayable and durable.

  • Small enough to port and trust.
  • Rich enough to replay live scientific loops.
  • Durable enough to survive higher-layer language evolution.

Different views for different people

One world does not mean one flat interface.

Different roles need different projections. The important constraint is that they should still be looking at the same underlying world, not separate shadow systems.

Scientist

Evidence and provenance view

  • Papers, notebook entries, external observations, measurement provenance.
  • Comparison between observed and expected behavior.
  • Confidence grounded in method, not just summary.

Data scientist

Simulation and disagreement view

  • Simulation contexts, run witnesses, deltas, and disagreement records.
  • Scenario branching without losing context.
  • Direct trace from model output to later decision state.

Engineer / platform

Replay and runtime view

  • Authored structure, lowering boundaries, adapters, and runtime seams.
  • Accepted history, replay path, transport, persistence, and execution context.
  • Enough visibility to trust how the system moved.

R&D lead / founder

Decision and policy view

  • Current readiness, open disagreement, repair status, and policy gates.
  • What changed, why it changed, and what still blocks promotion.
  • A defensible surface for real go/no-go calls.

Partner / funder / customer

External proof view

  • Simplified but trustworthy evidence-linked decision surface.
  • Enough witness to verify discipline without exposing internal chaos.
  • Confidence that the answer has a visible path behind it.
